前 3 轮见 [bug-hunt-2026-11.md](./bug-hunt-2026-11.md) 与 [bug-hunt-round2-3.md](./bug-hunt-round2-3.md)。

这三轮换了三个**此前完全没覆盖过**的角度，并引入了新手段。

## 新手段：并发黑盒打击

前几轮都是"读代码找并发问题"。第 4 轮改成**直接打**：
并发发 N 个请求打同一接口，然后断言最终数据（库存、购物车数量、订单数、券数）必须是什么。

好处：不依赖我读对代码，**竞态会自己暴露**。本轮第一条真 bug 就是这么抓到的
（10 个并发加购 → 购物车只剩 4 件）。

## 第 4 轮：并发与事务

### 修掉的

| # | 问题 | 后果 |
|---|---|---|
| 1 | **购物车加购丢单**：`existingItem.quantity + n` 读-改-写 → 10 个并发加购只记 4 件；组合包分支同样漏改 → 丢套数，且 99 套上限被绕过 | 用户狂点加入 → 购物车少记 → 下单少买 |
| 2 | **商品编辑把库存按绝对值写回 → 超卖**：运营打开弹窗时 stock=10，期间 3 笔订单各扣 1（库里已是 7），运营只改价格后保存（表单还带陈旧的 10）→ 库存被写回 10 | **凭空多出 3 件可卖，直接超卖** |
| 3 | **跨表锁顺序反转**：下单锁 Product→积分余额，取消锁 积分余额→Product | 40P01 死锁，重试后整单重做 |
| 4 | **合作方「设为默认地址」漏 Partner 父行锁** | 与 updateAddress 的两步写交错 → **两个默认地址** → 可能发错货 |
| 5 | **密码重置的 token_version 是读-改-写**（其余六处早已用 `literal`） | 并发重置时旧会话只失效一轮 |

### 并发打击护栏（8 条，都是"必须恒成立"的性质）

| 用例 | 断言 |
|---|---|
| CS-A 并发下单抢库存 | 库存 5、10 并发 → 成功正好 5、库存正好 0、**不为负** |
| CS-B 并发加购同一商品 | 10 次 → 购物车数量正好 10（**不能少记**） |
| CS-C 并发同幂等键下单 | 8 次 → 只创建 1 单、只扣 1 件库存 |
| CS-D 并发改密码 | token_version 递增、旧 token 立即失效 |
| CS-E 并发取消同一订单 | 库存**只回补一次**（不能虚增） |
| CS-F 10 用户并发抢 2 张券 | 只发出 2 张（**不能超发**） |
| CS-G 编辑弹窗开着时并发下单 | 保存编辑后库存仍是扣减后的值（**不能写回陈旧快照**） |
| CS-H 不带 stock_prev 改库存 | 400（拒绝用绝对值覆盖） |

### 复核为「不是 bug」的

- **幂等键**：`uniq_orders_user_client_key` 部分唯一索引确实存在 → 同 key 只成 1 单
- **积分余额**：全部走 `SELECT ... FOR UPDATE` + 绝对值 save + SAVEPOINT 兜底 → 并发安全
- **库存扣减**：四条路径都是 `WHERE stock >= n` 条件 UPDATE + 原子写 → 无超卖路径
- **领券**：模板行 FOR UPDATE → 总量/每人限领与发券同锁内串行化 → 不超发
- **事务内的网络/IO**：没有夹带

## 第 5 轮：领域规则（算得对不对）

不是"会不会崩"，而是**算得对不对**。

| # | 问题 | 后果 |
|---|---|---|
| 1 | **积分换购详情页把行积分当单价又乘一次数量** | 3 件 × 10 分显示成"每件 30 积分 × 3 = 90"，实际只扣 30 → **顾客看到被扣 3 倍积分** |
| 2 | **删除已发货/已完成订单**：积分流水被物理删除、余额不回退 | 每日体检永久报红；积分来源凭证凭空消失，无法对账 |
| 3 | **retention 清 730 天前的积分流水**：余额不动 | 体检「余额=流水累计」**永久不成立**；该用户老订单取消时 `earned=0` → **已发积分收不回来（白拿）** |
| 4 | **管理端把「待支付」改成「已支付」时积分永不发**（积分只在支付确认里发） | 状态已是"钱收到了"，客户却白少拿积分（1000 THB 少 10 分） |

### 演进：order_items 加 `line_total`（权威行小计）

组合包订单的明细行是"按权重把组合价分摊到组件行"的，
行权威金额是 `line_total`，但表里**只有 price（单价）** →
落库写的是 `round2(line_total / 行数量)`，**除不尽的尾差就丢了**。

实测：组合价 199.00（A 配比 3、B 配比 1），买 1000 套
→ A 行记 134190、B 行记 64800，明细合计 198990，而实收 199000 —— **差 10 THB**。

后果：订单详情逐行金额与实收对不上（用户看得见）+ 自家不变量必然报红。

修法：加一列 `line_total` 存权威行小计；落库 / 展示 / 体检统一用它。

### 演进：`archived_delta`（已归档流水净额）

retention 要清积分流水（控制表体积），但余额是用户资产不能动。
于是不变量「余额 = 流水累计」在清理之后永久不成立。

修法：清理时把被删流水的净额（按用户汇总）记到余额行的 `archived_delta`，
于是「余额 = 剩余流水累计 + 已归档净额」**永远精确成立**，用户积分一分没少。

### 复核为「不是 bug」的

- 同一张券不会用在多笔订单（事务内 `status='unused'` 条件 UPDATE 原子占位）
- 过期券 / 已用券 / 他人券 都在引擎与控制器两层拦住了
- 库存扣减与回补口径一致（含赠品与组合包组件）
- 多币种 `total_amount = round2(total_amount_thb × rate)` 与 `total_amount_thb` 自洽
- **「仅退款」不回补库存是对的**（refund 的语义就是"客户不退货、只退钱"；
  积分与券按"订单没成交"处理，与订单取消一致 —— 三者并不矛盾）

## 第 6 轮：性能与长期演进

### 复核为「不是 bug」的

- **N+1：0 处**。全仓扫"循环里 await 查库"，15 处候选**全是误报**
  （查询都在循环外，一次批量查 + Map 取）
- 批量导出、超时清扫、领券的循环都是**每批一次查询**的分页，不是 N+1

### 演进：让系统能自己发现慢接口

`/api/admin/metrics` 原来只有平均耗时 —— 但平均值骗人：
1000 个请求里 999 个 5ms、1 个 8 秒，平均 13ms 看着健康，而那个用户已经走了。

现在补上：
- `databasePool`（size / available / borrowed / pending）—— 排查"接口全卡住但 CPU 很低"的第一现场
- `slowRequests`（> 1s 的请求数）
- `slowestPaths` —— 最慢接口 Top 10（路径已归一化：`/api/orders/123` → `/api/orders/:id`，
  否则每个 id 一条记录，基数爆炸 + Top N 全是噪声）
