# CSV 导入 / 导出：列说明与差异

> 这份文档回答一个运营迟早会问的问题：**"导出出来的 CSV 怎么导不回去？"**

## 一句话结论

**导出的列 ≠ 导入的列，这是故意的。**

- **导出**是给人**看**的（对账、核对库存、给会计）→ 列多、含派生字段
- **导入**是给系统**读**的（建档、改档）→ 列少、只含主数据

两者服务的目的不同，强行做成对称反而会出问题（比如把"行小计"导进去，系统该信哪个？）。

## 各资源的列对照

### 商品（products）

| 列 | 导出 | 导入 | 说明 |
|---|:---:|:---:|---|
| `id` | ✅ | ✅ | 有 id = 更新该商品；无 id = 新建 |
| `name` | ✅ | ✅ **必填** | 商品名 |
| `name_th` | ✅ | ✅ | 泰文名（多语种搜索用） |
| `category` | ✅ | ✅ | **分类名**（不是 id）；找不到就报错 |
| `price` | ✅ | ✅ **必填** | 售价（THB） |
| `stock` | ✅ | ✅ | 库存，缺省 0 |
| `points` | ✅ | ✅ | 可抵扣积分，缺省 0 |
| `description` | ✅ | ✅ | 描述 |
| `image` | ✅ | ✅ | 本地路径原样保留；**填 http/https 远程地址会下载并转存本地** |

导出比导入多的：无（商品两侧是对称的）。

### 合作方（partners）

| 列 | 导出 | 导入 | 说明 |
|---|:---:|:---:|---|
| `id` | ✅ | ✅ | 有 id = 更新；无 id = 新建 |
| `login` | ✅ | ✅ **必填** | 登录名（字母/数字/点/下划线/连字符，2-100 位） |
| `display_name` | ✅ | ✅ | 商家名称 |
| `account_kind` | ✅ | ✅ | `dealer` 经销商 / `agent` 代理 |
| `discount_percent` | ✅ | ✅ | 统一折扣 0-100 |
| `is_active` | ✅ | ✅ | 启用 / 停用 |

导出比导入多的：无。

### 用户（users）

| 列 | 导出 | 导入 | 说明 |
|---|:---:|:---:|---|
| `id` | ✅ | ✅ | 有 id = 更新；无 id = 新建 |
| `nickname` | ✅ | ✅ **必填** | 昵称 |
| `username` | ✅ | ✅ | 不填则按 `区号+手机号` 生成 |
| `email` | ✅ | ✅ | 邮箱 |
| `phone` | ✅ | ✅ **必填** | 手机号（8-15 位数字） |
| `country_code` | ✅ | ✅ | `+86` / `+66` / `+60`；**不带 `+` 也认**（Excel 会把 `+66` 存成数字 66） |
| `referral_code` | ✅ | ✅ | 推荐码 |
| `is_active` | ✅ | ✅ | 启用 / 停用 |

导出比导入多的：无。

⚠️ **用户导入的密码不在列里** —— 这是故意的（见下）。

### 合作方订单（partner_orders）

| 列 | 导出 | 导入 | 说明 |
|---|:---:|:---:|---|
| 订单号 / 合作方 / 状态 / 收货人 / 电话 / 地址 / 总额 / 下单时间 | ✅ | ❌ | 只读导出 |
| 商品 ID / 快照名 / 数量 / 折扣快照 / 零售等价 / 单价 / 行小计 | ✅ | ❌ | 只读导出 |

**合作方订单只有导出，没有导入** —— 订单是系统生成的（下单 → 扣库存 → 发积分 → 生成优惠快照），
手工导入订单会绕过这一整套逻辑，把库存和账做乱。所以**刻意不做**。

## 两个必须知道的设计

### 1. 密码永远不进 CSV

导入账号时如果让运营在 CSV 里写密码，密码就会躺在邮件 / Excel / 聊天记录里 ——
一份泄露就是一批账号泄露。

所以：

- 系统生成**随机初始密码**，只在**导入结果里显示一次**
- 账号被标记 `must_reset_password = true`
- 用户首次登录后**必须改密**（服务端在账号级操作上拦截，返回 `PASSWORD_CHANGE_REQUIRED`）
- 运营永远不接触最终密码

合作方账号同理。

### 2. 导入默认"全有或全无"

默认模式是 `strict`：只要有一行有问题，**整批都不写入**。
理由：半截导入比不导入更糟 —— 运营会以为全导进去了。

大批量（几百行、只有几行写错）时，可以切到 `skip` 模式：
有问题的行被跳过并逐条回报，其余行正常导入。

## 怎么用

### 管理端

商品管理 / 用户管理 / 合作方管理页面都有「导入 CSV」「导出 CSV」按钮。

1. 点「导出 CSV」拿到当前数据（当模板用）
2. 在 Excel 里改（**别改表头**）
3. 点「导入 CSV」→ 选文件 → 预览
4. 预览会逐行报出哪行有什么问题
5. 选模式：
   - **严格**：有问题整批不导入（默认）
   - **跳过错误行**：只跳过有问题的行
6. 确认导入

### 命令行

```bash
# 导出当前商品
curl -H "Authorization: Bearer $TOKEN" \
  https://eshop.cider-bar.com/api/products/export.csv -o products.csv

# 预览（不写库）
curl -X POST -H "Authorization: Bearer $TOKEN" \
  -F "file=@products.csv" -F "dry_run=1" \
  https://eshop.cider-bar.com/api/products/import

# 真正导入（跳过错误行）
curl -X POST -H "Authorization: Bearer $TOKEN" \
  -F "file=@products.csv" -F "dry_run=false" -F "mode=skip" \
  https://eshop.cider-bar.com/api/products/import
```

## 常见问题

**Q：预览说"分类不存在"？**
A：CSV 里的 `category` 填的是**分类名**（如"食品"），不是 id。先在管理端把分类建好。

**Q：区号填 `66` 行不行？**
A：行。Excel 会把 `+66` 存成数字 `66`，两种写法都认。

**Q：图片列填远程地址安全吗？**
A：服务端会做 SSRF 防护（只允许 http/https、拒绝内网/环回/链路本地地址、
重定向逐跳复查、按内容哈希去重），但**仍然建议先自己下载好再传本地路径** ——
少一次外部请求就少一个风险面。

**Q：导出的 CSV 能直接导回去吗？**
A：商品 / 合作方 / 用户可以（列是对称的）；**合作方订单不行**（它是只读导出）。
