## 第 8 轮：授权矩阵（54 条路由逐条核对）

**先说结论**：三个文件（adminRoutes / partnerRoutes / orderRoutes）里**没有** `partners` 路由能被 operator 摸到，
没有写操作漏挂权限门，也没有 `/:id` 抢在 `/special` 前面的顺序坑 —— 接线本身是干净的。

但找到 2 条真问题 + 1 条纵深缺口：

| # | 问题 | 后果 | 修法 |
|---|---|---|---|
| 1 | **售后退款审批只挂 `orders` 权限** → operator（恰好有 orders）能对**任意用户的在途订单**批退款 | 资损级写操作（订单取消 + 收积分 + 收券 + 回补库存）。同文件「重置客户密码」早已用 `requireUserAdmin` 收口 —— 两边不对称 | 新增 `requireAdminOnly`，审批收口到 admin/super_admin。**列表仍然对 operator 开放**（看售后是客服的日常工作，不该误伤） |
| 2 | **管理端统计路由只有认证、没有资源级权限门** | 将来统计口径加入合作方/毛利，operator 会自动获得（与"合作方数据只给 admin"的设计意图冲突） | 补 `requirePermission('orders')`。现有角色能力**完全不变**，但多一道纵深，将来要收紧只改一处 |
| 3 | **异步导出任务的 4 个路由没有权限门**，类型权限只存在于控制器一层 | 第 1 轮修的正是这里（"合作方数据被判成 orders"）—— 只修在控制器，任何新路径绕过它就原样复发 | 路由层补最低门槛（orders），控制器仍按 type 精确判 —— 双层 |

> **纵深防御的价值**：控制器层的判断是"业务逻辑"，路由层的是"安全边界"。
> 前者会随功能演进被改，后者是最后一道闸。

## 第 12 轮：根治"永远绿的检查"（本轮由用户直接指出）

### 问题

第 9 轮加的 11 项引用完整性检查里，**大部分永远不可能报**。
原因很实在：那些外键是 `NO ACTION`，删父行会被数据库直接拒绝 → 孤儿行**根本产生不出来**。

但当时体检报告写着"✅ 11 项引用完整性全部通过" —— 这给了**虚假的安全感**：
真出问题那天它不会报警。更糟的是，如果口径写错，它还会**误报**，
把合法数据（比如 `carts.product_id IS NULL` 这种"商品已删、待清理"的合法状态）
判成违规，把真问题淹没在噪声里。

> **一条永远绿的检查，比没有检查更危险。**
> 没有检查 = 知道自己没在查；永远绿的检查 = 以为自己一直在查。

### 解法：每条检查必须二选一，否则元测试让 CI 变红

| 标记 | 含义 | 约束 |
|---|---|---|
| `selfTest` | 能造出违规数据（绕过应用层直接写库） | 元测试**实际跑一遍**，确认这条检查真抓到了。抓不到 → 测试失败 |
| `defensive: true` + `defensiveReason` | 明确写出它由哪个数据库约束保证 | 理由少于 10 个字 → 测试失败 |

**两者都没有 → 测试失败。** 这样"新增一条永远绿的检查"会被当场拦下。

### 落地的结果

- **23 条检查**（删掉 2 条重复的）：**13 条可自证** + **10 条显式防御**
- 每条防御项都写明"由哪个约束保证"，例如：
  `order_items.order_id → orders 是 NO ACTION 外键：删父行会被数据库直接拒绝，孤儿行产生不出来`
- 全库唯一**没有外键**的引用是 `after_sales.user_id` —— 这条是**真能报**的，已用自证证明
- 新增 `tests/api/invariantMeta.test.js`（IM-1..IM-6）作为元测试
- `scripts/check-data-invariants.mjs` 新增 `--self-test` 模式，可随时人工验证：
  ```
  NODE_ENV=test DATABASE_URL_TEST=... node scripts/check-data-invariants.mjs --self-test
  ```
  输出示例：
  ```
  ✅ stock_not_negative —— 造的违规数据被抓到了（1 行）
  🛡️  coupon_template_exists —— 防御项：user_coupons.template_id → coupon_templates 是 NO ACTION 外键
  ✅ 全部检查项都能证明自己会响
  ```

### 顺手补上的安全闸（自查时发现的真隐患）

`--self-test` 模式会 **TRUNCATE 表 + 写入违规数据**。
而脚本原本只有 `--allow-production` 这一个开关控制生产行为 ——
那个开关的语义是"允许在生产上跑**只读**重查询"，一旦有人顺手加上 `--self-test`，
就会**清空生产表**。

已加独立硬闸（不给 `--allow-production` 任何绕过能力）：
- `NODE_ENV=production` → 直接拒绝，退出码 2
- `NODE_ENV` 未设置 → 拒绝（此时连接串可能来自 `DATABASE_URL`，可能是生产库），除非显式 `--confirm-write`
- 并由 **IM-6 元测试**守护这条闸本身（防止以后被人拆掉）

## 第 13 轮：认证会话收口 + 回归流程漏洞

这一轮是被两件事逼出来的：① 后台 agent 抛下的线索"游客账号复用路径能否签发令牌"；
② 跑全量集成测试时撞出一个**真 bug**。两件事都指向同一个主题 —— **一致性**。

### 13-1 真问题：组合包重复加购后，接口返回的是旧数量

`tests/integration/bundle.test.js` 的 BD-7 挂了：加一次组合包（数量 1），再加一次，
期望数量 3，**实际返回 1**。

**根因不在组合包，在"原子更新"那一轮改造的收尾**。同一个控制器里：

| 分支 | 原子自增后 | 响应里的数量 |
|---|---|---|
| 普通商品（`cartController.js:253`） | 写完**重读** `freshItem` | ✅ 正确 |
| 组合包（`cartController.js:391`） | 写完**直接返回旧实例** | ❌ 旧值 |

`Cart.update({ quantity: literal('quantity + n') })` 改的是数据库，
`existingItem` 这个内存对象**还停在加购前的数字**。数据库里是 3，接口告诉前端是 1 ——
用户在购物车页看到的数量是错的，刷新一下才变。

> 为什么之前没发现：**回归只跑了 `tests/api` + `tests/vue`，漏了 `tests/integration`**。
> 而这个用例一直好好地躺在 `tests/integration/bundle.test.js` 里。
> **测了但没跑 = 没测。**

**已修**：组合包分支照普通商品分支的做法，原子更新后回读再返回。
**已加固**：部署脚本加了**回归门禁**（默认开启）—— 少跑一套测试就等于把那一套里的真 bug 放行到生产。

### 13-2 真问题：管理端的密码策略比别处松

"所有设密入口同一把尺子"是 AT-7 已经断言过的性质，但只覆盖了用户侧。
逐个 realm 核了一遍后，发现**权限最高的管理端反而最松**：

| 入口 | 原策略 | 现在 |
|---|---|---|
| `POST /api/admin/administrators`（创建管理员） | **完全不校验** | `assertPasswordPolicy` |
| `PUT /api/admin/administrators/:id/reset-password` | **只校验"≥6 个字符"** | `assertPasswordPolicy` |
| `POST /api/admin/init`（初始超管） | 只校验"≥8 字符" | `assertPasswordPolicy` |
| 用户注册/改密/重置、合作方创建/重置/自助改密 | `assertPasswordPolicy` | 不变 |

`123456` 在管理端是能被暴力猜到的，而管理端令牌能看全部订单、客户资料、导出与经营统计。

**已修**：三个入口统一走 `assertPasswordPolicy`（≥8 位 + 数字 + 字母）。
**不影响存量**：登录不校验策略，已有管理员的口令照常有效（不存在把人锁在门外的风险）。

### 13-3 演进：密码规则从"三份副本"收敛到"一份真相源"

改完后立刻暴露第二个问题：**前端有三份规则**（门户自带一份、合作方改密页抄一份、
管理端写死 `{ min: 6 }`）。后端一收紧，前端就会变成"前端校验过了、后端返回 400"的错位。

- 新增 `src/utils/passwordPolicy.js`（共享层，**唯一**规则实现）
- 门户那份改为转发（既有 import 路径不变）、合作方改密页改为引用
- 管理端 `Operators.vue` 改用共享层校验，三语文案同步
- 新增 `tests/vue/passwordPolicyParity.test.js`：**行为比对**前后端判定结论（不是源码 diff，
  实现怎么改都不会误报），并断言"没有第二份副本"

### 13-4 纵深：生产漏配密钥会静默抹平密钥域边界

`resolveScopedSecret` 在生产未配置 `JWT_ADMIN_SECRET` 时，**直接回退到 `JWT_SECRET`**。
于是"用户 / 管理端 / 合作方"三把密钥变成同一把 —— 边界只剩载荷里的 `type` 字段；
某一域的密钥单独泄露，就能伪造其它域的令牌。

- 生产回退改为**从主密钥派生**一把独立子密钥（HMAC，确定性 → 重启/扩容不影响）
- 新增 `JWT_SECRET_ISOLATION`（只有布尔结论、无密钥内容），接入管理端运行时指标 ——
  运维在指标里就能看到"三把密钥是否真的互不相同"，而不是只能翻日志
- 显式配成同一个值时**如实报告不隔离**，不粉饰

生产实测：三把密钥本来就各自独立（sha8 互不相同），这次改的是**未来漏配时的兜底行为**。

### 13-5 复核为误报

- "游客账号复用能签发令牌" → **已修**：复用分支只回手机号 + `accountReused`，不发 token
  （新账号才发）。并发竞态分支同样不发。
- "初始管理员口令可能被爆破" → 生产 `INIT_ADMIN_PASSWORD` 未设置、管理员早已初始化，
  且登录有 `loginLimiter` + 失败验证码兜底
- 读文件时看到 `guestAccountCleanup.js` 疑似大面积损坏（`must_reset_stren`、`for (const candidate candidates)`）——
  **是工具输出的显示失真**：原始字节与 `node --check` 都证明文件是好的。
  这类"看起来像 bug 的乱码"必须先核字节再下结论。

## 第 14 轮：逻辑关联的悬空引用 + 体检系统自身的错误

这一轮从**"引用完整性"**这条线继续挖，结果挖出了三件事：
两个真 bug、**体检系统自己的一批错误**，以及一个**推翻前几轮结论**的发现。

### 14-1 真 bug：删掉订单后，抵扣券永远卡在"已使用"

模型注释里其实写着约定：

> `used_by_order_id` 仅逻辑关联 orders.id：订单允许硬删，不建外键约束
> （**释放先于删单完成**）

而删单路径只在**未履约**状态（pending/paid/shipping）走了 `restoreOrderResources`
顺带释放券 —— **已履约订单删除时，没人释放**：

| 删单时的订单状态 | 券的结局（修之前） |
|---|---|
| pending / paid / shipping | 退回 `unused` ✅ |
| shipped / delivered / completed | **卡在 `used`，且 `used_by_order_id` 指向已不存在的订单** ❌ |

后果：用户在「我的优惠券」里看到一张永远"已使用"、再也用不了的券，
而它挂着一个**幽灵订单**。

**已修**：删单时**无条件**释放券（删单之前完成，符合模型注释的约定）。
不动库存与积分 —— 货确实发出去了，回补会虚增。
**已加体检项** `coupon_used_order_exists`：已用券挂的订单必须真实存在
（`used_by_order_id` 无外键，这项**真能报**）。

### 14-2 真 bug：删掉组合包，购物车里留下悬空/僵尸行

组合包是**硬删**（`Bundle` 无 paranoid），删除时只清了 `bundle_items`，
**没清购物车里的组合包行**。而 `carts.bundle_id` 在**生产库没有外键**。

两个库的结局还不一样：

- 测试库：FK 是 `SET NULL` → 留下一行 `product_id` 与 `bundle_id` **双 NULL** 的僵尸行；
- 生产库：没有 FK → 留下一行指向**幽灵组合包**的记录。

前端 `Checkout.availableCartItems` 会把这类行过滤掉（排除在下单之外），
所以**结算不会被卡死**（我一开始的假设被证伪），但用户会在购物车页
看到一条**没有名称的"失效商品"**行。

**已修**：删组合包时显式清理购物车行，两个库结局一致。
**护栏**：黑盒用例断言"**整行**消失"—— 只查 `bundle_id` 会误判成"已清理"
（测试库的 FK 把它置成 NULL 了），这类弱断言在反向验证时果然没变红。

### 14-3 体检系统自身的三个错误（第 12 轮的成果被自己推翻）

| # | 错误 | 怎么发现的 |
|---|---|---|
| 1 | `coupon_template_exists` 与 `user_coupon_template_exists` **查的是同一件事**（同一张表同一列） | IM-1 只查**名称**不重复，查不出语义重复 → 新增 **IM-1b**（按 FROM/JOIN/WHERE 归一化比对） |
| 2 | `after_sale_order_exists` 被标成"防御项（由外键保证，应用层造不出）" —— **那是错的**：`after_sales.order_id` **根本没有外键** | 审计生产库外键集合时发现 → 改成真检查并补 selfTest |
| 3 | `cart_product_exists` 的理由写成"SET NULL 外键"，生产库实际是 **NO ACTION** | 同上 |

第 2 条的代价比看起来大：它让第 9 轮的结论"**全库唯一没有外键保护的引用是
`after_sales.user_id`**"也一起错了 —— 实际是 **14 个**。

### 14-4 推翻前几轮结论：测试库与生产库的外键集合**不一致**

把生产库和测试库的外键逐条列出来对比：

| 列 | 测试库 | 生产库 |
|---|---|---|
| `carts.bundle_id → bundles` | **SET NULL** | **无外键** |
| `carts.product_id → products` | **SET NULL** | **NO ACTION** |
| `carts.user_id → users` | SET NULL | SET NULL ✅ |

原因：测试库是 `sequelize.sync()` 按**模型定义**建的，模型里有这些关联；
生产库是手工 DDL 建的，这些 FK 从来没补上。

影响：
- 体检项的**自证在两个库上跑的约束条件不同**（测试库插不进悬空行，生产库能）；
- 第 9 轮那份"外键覆盖"表**是照着模型定义写的，不是照着生产库查的** ——
  于是 4 个"防御项"的理由写错、1 个检查被误标成不可能发生。

**这一轮只做认知修正，没有动生产库的表结构**（加外键属于结构变更，
且存量数据要重新校验，风险不在"扒拉问题"该动的范围内）。

生产库实测：14 个无外键保护的 `*_id` 列，**当前悬空行数全部为 0**。

### 14-5 复核为误报（本轮查过但**不是** bug 的）

- **"删组合包会把客户整个结算卡死"** → 证伪：前端 `availableCartItems` 已过滤失效行。
- **"sharp 模块在生产上坏了"** → 旧日志（Node 18 vs sharp 0.35 的老账）；
  `package.json` 把 sharp **精确锁定 0.33.5**，生产实测加载正常。
- **"游客账号复用路径还能签发令牌"** → 已修：复用分支只回手机号 + `accountReused`，不发 token。

### 14-6 方法论：不变量的"保证方"不一定是数据状态

一开始想给"购物车组合包行必须指向存在的组合包"加一条数据体检，
结果发现要自证就得在测试库里插一条违反外键的行 ——
而测试库的 FK 比生产库全，插不进去（PG 里 `DROP CONSTRAINT` + 同事务 `INSERT`
还会挂起）。

**停下来重新想：这��不变量的正确保证方是应用行为（删组合包时清理购物车行），
不是数据状态。** 那就该用**黑盒行为测试**守（删组合包 → 购物车行消失），
而不是用数据体检（体检只能证明"数据当前没坏"，证明不了"以后不会坏"）。

> 数据体检适合守**"数据被外部写坏"**的类目（脚本、迁移、并发、人工改库）；
> 应用自己制造的数据，用**行为测试**守更直接、也更便宜。

### 15-1 金额守恒：把"不多收钱"升级成"不多不少"

抓不到**少收**（实收 < 各行应付之和 = 账单对不上）。

真值是恒等式：`total_amount_thb == Σ(line_total - discount_allocated)`。

用**组合矩阵**实测（不是单点）：无优惠 / 商品直降 / 满减 / 券 / 满减+券 /
组合包（权重除不尽）+券 / 买多赠一 / 组合包+满减+券 —— 8 种组合全部成立。

**新增**：
- 体检项 `order_total_equals_lines_payable`（含自证）
- `tests/api/moneyConservation.test.js`：9 条用例，含一条**积分兑换单不被误报**
  （积分单实收记 0、行里是 THB 参考价，两者本就不该相等）

## 第 16 轮：业务时区可配 + 已删商品不复活（两项业务决策落地）

第 15 轮结尾列了两个"需要产品/运维决策、不属于扒拉问题"的点，用户拍板：
**下架不复活已删商品**、**今天依赖时间可配**。这一轮把它们落成代码。

### 16-1 业务时区可配（`business_timezone`）

**原来的问题**：所有"今天"都跟着**服务器进程的本地时区**走 ——
`new Date().setHours(0,0,0,0)` 与 `AT TIME ZONE '<服务器偏移>'`。
服务器换个时区，"今日营收"就跟着变；有夏令时的时区上，
固定偏移的日分桶还会与日历日筛选**差一小时**。

**改造范围**（四个模块的"今天"口径，全部收口到一处）：

| 模块 | 原来 | 现在 |
|---|---|---|
| 统计日分桶 | `AT TIME ZONE '<服务器偏移>'` | `AT TIME ZONE '<配置时区>'`（IANA 名，PG 逐行求偏移，DST 也对） |
| 订单「今日营收」 | 服务器本地零点 | 业务时区零点 |
| 用户「今日新增/近7天/近30天」 | 服务器本地零点 | 业务时区零点 |
| 订单列表 / 导出 / 积分流水的日期筛选 | 服务器本地日历日 | 业务时区日历日 |

**关键实现细节**：
- 时区名会被拼进 SQL（`AT TIME ZONE '...'`）→ **只接受能通过 `Intl.DateTimeFormat`
  校验的真实 IANA 名**，非法值一律 400（顺带挡掉注入）；
- 日分桶用 **IANA 名而不是固定偏移** —— 固定偏移在 DST 时区上会逐行算错；
- **夏令时切换日本地日只有 23/25 小时**："本地日终点"必须按当地 23:59:59.999 单独换算，
  写成"起点 + 24h - 1ms"会漏掉/多算边界那一小时（这条是被 DST 测试当场抓出来的）；
- 统计缓存键**带上时区**，否则改完配置 15 秒内还会读到旧口径。

**默认值 `Asia/Shanghai`**：与生产服务器当前时区一致（实测 `Intl...resolvedOptions().timeZone = Asia/Shanghai`），
所以**升级后数字一个不变**；要按泰国时间运营，改配置成 `Asia/Bangkok` 即可。

**管理端**：系统配置页新增「业务时区」卡片（可搜索下拉 + 手动输入），三语文案齐全。

**测试**：
- `tests/api/businessTimezone.test.js`（7 条）：时区名校验（含 4 种注入尝试）、
  偏移（含美东冬夏令时）、日边界（含 23 小时的 DST 日）、日历日加减不溢出、
  7 天序列、SQL 表达式、配置读取与回退
- `tests/api/businessTimezoneWiring.test.js`（4 条）：**冻结时钟**后从 HTTP 入口证明
  「今日营收」与「日期筛选」真的跟着配置走、缓存不串味、配置接口拒绝非法时区名

### 16-2 已删商品不被上下架复活

业务约定：**上下架不复活已删商品，只有显式 `restore` 能让它回来。**

现状核查（三条路径）：
| 路径 | 行为 | 结论 |
|---|---|---|
| 批量上下架 | `Product.update` 默认带 `deleted_at IS NULL` → 已删行不参与 | ✅ 符合约定 |
| 改商品字段 | `findByPk(id, {paranoid:false})` → 能改到已删行，但 **deleted_at 不清** → 不会复活 | ✅ 符合约定 |
| `POST /:id/restore` | 显式 `paranoid:false` + 清 `deleted_at` | ✅ 唯一的复活路径 |

**风险在于"顺手"**：哪天有人为了"修批量上架不生效"加一句 `paranoid: false`，
删除这个动作就形同虚设（删了还能批量上架回来），而且当场没人会发现。

**已做**：
- 代码里把这条约定**写死成注释**（说明为什么这里故意不加 `paranoid: false`）
- 新增护栏 `tests/api/deletedProductNotRevived.test.js`（4 条）：
  批量上架不复活、批量下架不误伤、改字段不复活、只有 restore 能回来
- **反向验证**：故意加上 `paranoid: false` → 护栏立刻变红 ✅

### 18-5 功能优化盘点（基于生产库实测，不是凭感觉）

**实测前提**：生产数据量很小（9 单 / 18 商品 / 3 用户），所有热点查询都在 **0.1ms 内**，
当前的 seq scan 是小表的正确选择 —— **当下没有可测的性能问题**。
优化空间都在"数据长大后"，所以下面每条都有**证据**：

| # | 优化点 | 证据 | 做法 |
|---|---|---|---|
| O1 | `users.last_login_at` **无索引** | 生产库逐列核对：users 有 12 个索引，**没有 last_login_at** → 仪表盘"近 7 天活跃用户"每次**全表扫 users**（增长最快的表，且面板每 30 秒自动刷新） | 加迁移 `013_users_last_login_at_index`（CONCURRENTLY，不锁表） |
| O2 | 仪表盘**每个数字一条 count** | 实测发 **10 条查询**，orders 表**全表扫 5 遍** | 用 PG 的 `FILTER` 合并成 **6 条**，orders 只扫 3 遍；**口径一个数字都没变**（dashboard.actionable + revenueConsistency 用例逐项相等） |
| O3 | 超时清扫的 N+1 | 每单一个事务 + 行锁复查（2N 次查询） | **不改**：这是刻意的并发设计（与支付确认互斥），批量取明细会让"取到的明细已过期" → 重复回补库存。宁可慢，不可错 |
| O4 | 批量改状态的 N+1 | 每单 3 次查询（积分流水 / 余额 / 明细） | **已做**：整批流水与明细各一条查询拿完 + 余额行实例与积分服务共用。实测 10 单 **106 → 68 条**（见下） |

#### O4 的实现（以及一处被纠正的建议）

**做法**：
1. 整批订单的**购物积分流水**与**订单明细**各一条查询拿完
   （原来每单各查一次；earn 流水还被查了**两遍** —— 守卫一次、`restoreOrderResources` 内部又一次）；
2. 守卫查到的**余额行实例**传给积分服务复用 → 每单少查一次余额
   （行锁已经在手，实例里的 `balance` 会被服务就地更新 → 语义不变）。

**实测**：批量取消 10 单 **106 条 → 68 条**（-36%）。不可省的是每单的写操作
（库存 / 订单 / 流水 / 余额各一次 ≈ 5 条），省掉的是**读**：50 条读 → 16 条。

> ⚠️ **一处我原先的建议是错的，已纠正**：我最初说"按用户缓存余额行"——
> **不行**。前一张单回收积分后余额就变了，后一张单的守卫必须看到**最新**余额，
> 缓存会让守卫用旧值判断，可能放行本该拦的单。
> 正确做法是：**仍然每单读一次**，但把同一个**已加行锁的实例**同时交给守卫和积分服务。

**正确性护栏**（`tests/api/bulkCancelResources.test.js`，5 条）：
库存恰好回补 N 件 / 积分恰好收回 N 笔且余额 == 流水累计 / 券退回未使用 /
积分已被花掉的单被跳过而其余照常回补 / 查询条数 ≤ 80。

**反向验证**：撤掉优化 → BC-5 变红（106 > 80），而 BC-1~BC-4 仍绿
（它们守的是正确性，与性能无关 —— 这正是分开写的原因）。

**护栏**：新增 `dashboardQueryCount.test.js` —— 断言总览数据方法的查询条数 **≤ 8**
（当前 6）。守的是"形状"而不是"数字"：数字对不对有别的用例管，
这里管的是"又多写了一条 count"这种最容易犯的性能退化。
已反向验证：撤掉合并 → 10 条 → 护栏变红 ✅

### 这轮的方法论收获

1. **生产库实测比读代码硬**：外键覆盖、SET NULL 的合法状态、5 条软删商品的历史订单 —— 都是读代码看不出来的
2. **护栏测试的"永远绿"陷阱**：我加的第一版孤儿检查因为外键保护**根本不可能触发**，
   等于假检查 → 改成用唯一无外键的 `after_sales.user_id` 来证明它真能报
3. **扫描脚本本身会误报**：文本插值、slot 包装组件都要排除，否则噪声淹没真问题
4. **"检查全绿"本身需要被检查**：检查项要能自证会响（`selfTest`），
   或者说清"由什么约束保证"（`defensive`）—— 否则体检报告只是心理安慰

5. **"测了但没跑"和"没测"一样危险**：组合包数量回读的 bug 用例一直存在，
   只是回归漏了 `tests/integration` —— 少跑一套测试 = 把那一套里的真 bug 放行到生产。
   现在部署脚本带**回归门禁**（默认开启）。

6. **"测试库和生产库不一样"**：测试库是 `sequelize.sync()` 建的（按模型定义），
   生产库是手工 DDL 建的 —— 外键集合并不一致。照着模型定义写"外键覆盖"结论，
   等于照着错误的地图数路。**要查就查真正在跑的那个库。**

**生产数据**：八轮全程 3 用户 / 9 订单 / 9 明细 / 18 商品 / 2 合作方 / 1 管理员，**一次没变**；
数据不变量（23 项：15 自证 + 8 防御）每次全过。
