## 第 8 轮：授权矩阵（54 条路由逐条核对）

**先说结论**：三个文件（adminRoutes / partnerRoutes / orderRoutes）里**没有** `partners` 路由能被 operator 摸到，
没有写操作漏挂权限门，也没有 `/:id` 抢在 `/special` 前面的顺序坑 —— 接线本身是干净的。

但找到 2 条真问题 + 1 条纵深缺口：

| # | 问题 | 后果 | 修法 |
|---|---|---|---|
| 1 | **售后退款审批只挂 `orders` 权限** → operator（恰好有 orders）能对**任意用户的在途订单**批退款 | 资损级写操作（订单取消 + 收积分 + 收券 + 回补库存）。同文件「重置客户密码」早已用 `requireUserAdmin` 收口 —— 两边不对称 | 新增 `requireAdminOnly`，审批收口到 admin/super_admin。**列表仍然对 operator 开放**（看售后是客服的日常工作，不该误伤） |
| 2 | **管理端统计路由只有认证、没有资源级权限门** | 将来统计口径加入合作方/毛利，operator 会自动获得（与"合作方数据只给 admin"的设计意图冲突） | 补 `requirePermission('orders')`。现有角色能力**完全不变**，但多一道纵深，将来要收紧只改一处 |
| 3 | **异步导出任务的 4 个路由没有权限门**，类型权限只存在于控制器一层 | 第 1 轮修的正是这里（"合作方数据被判成 orders"）—— 只修在控制器，任何新路径绕过它就原样复发 | 路由层补最低门槛（orders），控制器仍按 type 精确判 —— 双层 |

> **纵深防御的价值**：控制器层的判断是"业务逻辑"，路由层的是"安全边界"。
> 前者会随功能演进被改，后者是最后一道闸。

**数据很干净。** 但暴露一个真问题：这些检查**只在我手写脚本里跑，没进每日体检** —— 将来某次写入把关联行删了，要等客户投诉才发现。

### 演进：11 项引用完整性检查固化进体检

同时查清了**外键覆盖**（这决定了哪些检查是"真检查"、哪些是"外键已保证的防御"）：

| 外键行为 | 表 | 孤儿可能性 |
|---|---|---|
| NO ACTION | order_items / orders / after_sales.order_id / user_coupons / partner_orders / order_promotions / bundle_items | 删父行会被 DB 拦住 → 孤儿不可能（检查为防御） |
| SET NULL | carts.product_id / carts.user_id / point_transactions.order_id / products.category_id | 置 NULL 是**合法状态** → 检查必须排除 NULL，否则**误报** |
| CASCADE | point_transactions.user_id / user_point_balances.user_id | 级联删除 → 孤儿不可能 |
| **无外键** | **after_sales.user_id** | **唯一真能出现孤儿的引用** → 这项能真报出来（已用测试证明） |

> 差点踩坑：最初我把检查写成 `LEFT JOIN ... WHERE x IS NULL`，那会把
> `carts.product_id IS NULL`（商品已删、待清理）**误判成违规**。已修正。

## 第 10 轮：前端可访问性

### 真问题：13 个"只有图标"的按钮没有可访问名称

购物车里"删除商品""减少数量"（最高频的操作）只有图标没有文字，
屏幕阅读器只能读出"按钮" —— 用户完全不知道按下去会发生什么（WCAG 4.1.2）。

**已修**：购物车 9 处 + 商品详情 1 处 + 登录页密码可见 1 处 + Toast 关闭 2 处，三语文案。

**防退化**：新增护栏测试，扫全部前端模板，新增"无名图标按钮"直接让测试变红。

### 复核为误报的

- Profile.vue 的 5 个标签按钮 → 其实**有文字**（`{{ t('profile.myOrders') }}`），是我的扫描脚本把插值去掉后误判
- Ripple.vue → 是 `<button><slot/></button>` 的**包装基类**，真实按钮在父组件里 → 护栏测试里已跳过

## 第 11 轮：移动端触控热区
