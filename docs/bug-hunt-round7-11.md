## 第 8 轮：授权矩阵（54 条路由逐条核对）

**先说结论**：三个文件（adminRoutes / partnerRoutes / orderRoutes）里**没有** `partners` 路由能被 operator 摸到，
没有写操作漏挂权限门，也没有 `/:id` 抢在 `/special` 前面的顺序坑 —— 接线本身是干净的。

但找到 2 条真问题 + 1 条纵深缺口：

| # | 问题 | 后果 | 修法 |
|---|---|---|---|
| 1 | **售后退款审批只挂 `orders` 权限** → operator（恰好有 orders）能对**任意用户的在途订单**批退款 | 资损级写操作（订单取消 + 收积分 + 收券 + 回补库存）。同文件「重置客户密码」早已用 `requireUserAdmin` 收口 —— 两边不对称 | 新增 `requireAdminOnly`，审批收口到 admin/super_admin。**列表仍然对 operator 开放**（看售后是客服的日常工作，不该误伤） |
| 2 | **管理端统计路由只有认证、没有资源级权限门** | 将来统计口径加入合作方/毛利，operator 会自动获得（与"合作方数据只给 admin"的设计意图冲突） | 补 `requirePermission('orders')`。现有角色能力**完全不变**，但多一道纵深，将来要收紧只改一处 |
| 3 | **异步导出任务的 4 个路由没有权限门**，类型权限只存在于控制器一层 | 第 1 轮修的正是这里（"合作方数据被判成 orders"）—— 只修在控制器，任何新路径绕过它就原样复发 | 路由层补最低门槛（orders），控制器仍按 type 精确判 —— 双层 |

> **纵深防御的价值**：控制器层的判断是"业务逻辑"，路由层的是"安全边界"。
> 前者会随功能演进被改，后者是最后一道闸。

## 第 12 轮：根治"永远绿的检查"（本轮由用户直接指出）

### 问题

第 9 轮加的 11 项引用完整性检查里，**大部分永远不可能报**。
原因很实在：那些外键是 `NO ACTION`，删父行会被数据库直接拒绝 → 孤儿行**根本产生不出来**。

但当时体检报告写着"✅ 11 项引用完整性全部通过" —— 这给了**虚假的安全感**：
真出问题那天它不会报警。更糟的是，如果口径写错，它还会**误报**，
把合法数据（比如 `carts.product_id IS NULL` 这种"商品已删、待清理"的合法状态）
判成违规，把真问题淹没在噪声里。

> **一条永远绿的检查，比没有检查更危险。**
> 没有检查 = 知道自己没在查；永远绿的检查 = 以为自己一直在查。

### 解法：每条检查必须二选一，否则元测试让 CI 变红

| 标记 | 含义 | 约束 |
|---|---|---|
| `selfTest` | 能造出违规数据（绕过应用层直接写库） | 元测试**实际跑一遍**，确认这条检查真抓到了。抓不到 → 测试失败 |
| `defensive: true` + `defensiveReason` | 明确写出它由哪个数据库约束保证 | 理由少于 10 个字 → 测试失败 |

**两者都没有 → 测试失败。** 这样"新增一条永远绿的检查"会被当场拦下。

### 落地的结果

- **23 条检查**（删掉 2 条重复的）：**13 条可自证** + **10 条显式防御**
- 每条防御项都写明"由哪个约束保证"，例如：
  `order_items.order_id → orders 是 NO ACTION 外键：删父行会被数据库直接拒绝，孤儿行产生不出来`
- 全库唯一**没有外键**的引用是 `after_sales.user_id` —— 这条是**真能报**的，已用自证证明
- 新增 `tests/api/invariantMeta.test.js`（IM-1..IM-6）作为元测试
- `scripts/check-data-invariants.mjs` 新增 `--self-test` 模式，可随时人工验证：
  ```
  NODE_ENV=test DATABASE_URL_TEST=... node scripts/check-data-invariants.mjs --self-test
  ```
  输出示例：
  ```
  ✅ stock_not_negative —— 造的违规数据被抓到了（1 行）
  🛡️  coupon_template_exists —— 防御项：user_coupons.template_id → coupon_templates 是 NO ACTION 外键
  ✅ 全部检查项都能证明自己会响
  ```

### 顺手补上的安全闸（自查时发现的真隐患）

`--self-test` 模式会 **TRUNCATE 表 + 写入违规数据**。
而脚本原本只有 `--allow-production` 这一个开关控制生产行为 ——
那个开关的语义是"允许在生产上跑**只读**重查询"，一旦有人顺手加上 `--self-test`，
就会**清空生产表**。

已加独立硬闸（不给 `--allow-production` 任何绕过能力）：
- `NODE_ENV=production` → 直接拒绝，退出码 2
- `NODE_ENV` 未设置 → 拒绝（此时连接串可能来自 `DATABASE_URL`，可能是生产库），除非显式 `--confirm-write`
- 并由 **IM-6 元测试**守护这条闸本身（防止以后被人拆掉）

## 第 13 轮：认证会话收口 + 回归流程漏洞

这一轮是被两件事逼出来的：① 后台 agent 抛下的线索"游客账号复用路径能否签发令牌"；
② 跑全量集成测试时撞出一个**真 bug**。两件事都指向同一个主题 —— **一致性**。

### 13-1 真问题：组合包重复加购后，接口返回的是旧数量

`tests/integration/bundle.test.js` 的 BD-7 挂了：加一次组合包（数量 1），再加一次，
期望数量 3，**实际返回 1**。

**根因不在组合包，在"原子更新"那一轮改造的收尾**。同一个控制器里：

| 分支 | 原子自增后 | 响应里的数量 |
|---|---|---|
| 普通商品（`cartController.js:253`） | 写完**重读** `freshItem` | ✅ 正确 |
| 组合包（`cartController.js:391`） | 写完**直接返回旧实例** | ❌ 旧值 |

`Cart.update({ quantity: literal('quantity + n') })` 改的是数据库，
`existingItem` 这个内存对象**还停在加购前的数字**。数据库里是 3，接口告诉前端是 1 ——
用户在购物车页看到的数量是错的，刷新一下才变。

> 为什么之前没发现：**回归只跑了 `tests/api` + `tests/vue`，漏了 `tests/integration`**。
> 而这个用例一直好好地躺在 `tests/integration/bundle.test.js` 里。
> **测了但没跑 = 没测。**

**已修**：组合包分支照普通商品分支的做法，原子更新后回读再返回。
**已加固**：部署脚本加了**回归门禁**（默认开启）—— 少跑一套测试就等于把那一套里的真 bug 放行到生产。

### 13-2 真问题：管理端的密码策略比别处松

"所有设密入口同一把尺子"是 AT-7 已经断言过的性质，但只覆盖了用户侧。
逐个 realm 核了一遍后，发现**权限最高的管理端反而最松**：

| 入口 | 原策略 | 现在 |
|---|---|---|
| `POST /api/admin/administrators`（创建管理员） | **完全不校验** | `assertPasswordPolicy` |
| `PUT /api/admin/administrators/:id/reset-password` | **只校验"≥6 个字符"** | `assertPasswordPolicy` |
| `POST /api/admin/init`（初始超管） | 只校验"≥8 字符" | `assertPasswordPolicy` |
| 用户注册/改密/重置、合作方创建/重置/自助改密 | `assertPasswordPolicy` | 不变 |

`123456` 在管理端是能被暴力猜到的，而管理端令牌能看全部订单、客户资料、导出与经营统计。

**已修**：三个入口统一走 `assertPasswordPolicy`（≥8 位 + 数字 + 字母）。
**不影响存量**：登录不校验策略，已有管理员的口令照常有效（不存在把人锁在门外的风险）。

### 13-3 演进：密码规则从"三份副本"收敛到"一份真相源"

改完后立刻暴露第二个问题：**前端有三份规则**（门户自带一份、合作方改密页抄一份、
管理端写死 `{ min: 6 }`）。后端一收紧，前端就会变成"前端校验过了、后端返回 400"的错位。

- 新增 `src/utils/passwordPolicy.js`（共享层，**唯一**规则实现）
- 门户那份改为转发（既有 import 路径不变）、合作方改密页改为引用
- 管理端 `Operators.vue` 改用共享层校验，三语文案同步
- 新增 `tests/vue/passwordPolicyParity.test.js`：**行为比对**前后端判定结论（不是源码 diff，
  实现怎么改都不会误报），并断言"没有第二份副本"

### 13-4 纵深：生产漏配密钥会静默抹平密钥域边界

`resolveScopedSecret` 在生产未配置 `JWT_ADMIN_SECRET` 时，**直接回退到 `JWT_SECRET`**。
于是"用户 / 管理端 / 合作方"三把密钥变成同一把 —— 边界只剩载荷里的 `type` 字段；
某一域的密钥单独泄露，就能伪造其它域的令牌。

- 生产回退改为**从主密钥派生**一把独立子密钥（HMAC，确定性 → 重启/扩容不影响）
- 新增 `JWT_SECRET_ISOLATION`（只有布尔结论、无密钥内容），接入管理端运行时指标 ——
  运维在指标里就能看到"三把密钥是否真的互不相同"，而不是只能翻日志
- 显式配成同一个值时**如实报告不隔离**，不粉饰

生产实测：三把密钥本来就各自独立（sha8 互不相同），这次改的是**未来漏配时的兜底行为**。

### 13-5 复核为误报

- "游客账号复用能签发令牌" → **已修**：复用分支只回手机号 + `accountReused`，不发 token
  （新账号才发）。并发竞态分支同样不发。
- "初始管理员口令可能被爆破" → 生产 `INIT_ADMIN_PASSWORD` 未设置、管理员早已初始化，
  且登录有 `loginLimiter` + 失败验证码兜底
- 读文件时看到 `guestAccountCleanup.js` 疑似大面积损坏（`must_reset_stren`、`for (const candidate candidates)`）——
  **是工具输出的显示失真**：原始字节与 `node --check` 都证明文件是好的。
  这类"看起来像 bug 的乱码"必须先核字节再下结论。

## 第 14 轮：逻辑关联的悬空引用 + 体检系统自身的错误

这一轮从**"引用完整性"**这条线继续挖，结果挖出了三件事：
两个真 bug、**体检系统自己的一批错误**，以及一个**推翻前几轮结论**的发现。

### 14-1 真 bug：删掉订单后，抵扣券永远卡在"已使用"

模型注释里其实写着约定：

> `used_by_order_id` 仅逻辑关联 orders.id：订单允许硬删，不建外键约束
> （**释放先于删单完成**）

而删单路径只在**未履约**状态（pending/paid/shipping）走了 `restoreOrderResources`
顺带释放券 —— **已履约订单删除时，没人释放**：

| 删单时的订单状态 | 券的结局（修之前） |
|---|---|
| pending / paid / shipping | 退回 `unused` ✅ |
| shipped / delivered / completed | **卡在 `used`，且 `used_by_order_id` 指向已不存在的订单** ❌ |

后果：用户在「我的优惠券」里看到一张永远"已使用"、再也用不了的券，
而它挂着一个**幽灵订单**。

**已修**：删单时**无条件**释放券（删单之前完成，符合模型注释的约定）。
不动库存与积分 —— 货确实发出去了，回补会虚增。
**已加体检项** `coupon_used_order_exists`：已用券挂的订单必须真实存在
（`used_by_order_id` 无外键，这项**真能报**）。

### 14-2 真 bug：删掉组合包，购物车里留下悬空/僵尸行

组合包是**硬删**（`Bundle` 无 paranoid），删除时只清了 `bundle_items`，
**没清购物车里的组合包行**。而 `carts.bundle_id` 在**生产库没有外键**。

两个库的结局还不一样：

- 测试库：FK 是 `SET NULL` → 留下一行 `product_id` 与 `bundle_id` **双 NULL** 的僵尸行；
- 生产库：没有 FK → 留下一行指向**幽灵组合包**的记录。

前端 `Checkout.availableCartItems` 会把这类行过滤掉（排除在下单之外），
所以**结算不会被卡死**（我一开始的假设被证伪），但用户会在购物车页
看到一条**没有名称的"失效商品"**行。

**已修**：删组合包时显式清理购物车行，两个库结局一致。
**护栏**：黑盒用例断言"**整行**消失"—— 只查 `bundle_id` 会误判成"已清理"
（测试库的 FK 把它置成 NULL 了），这类弱断言在反向验证时果然没变红。

### 14-3 体检系统自身的三个错误（第 12 轮的成果被自己推翻）

| # | 错误 | 怎么发现的 |
|---|---|---|
| 1 | `coupon_template_exists` 与 `user_coupon_template_exists` **查的是同一件事**（同一张表同一列） | IM-1 只查**名称**不重复，查不出语义重复 → 新增 **IM-1b**（按 FROM/JOIN/WHERE 归一化比对） |
| 2 | `after_sale_order_exists` 被标成"防御项（由外键保证，应用层造不出）" —— **那是错的**：`after_sales.order_id` **根本没有外键** | 审计生产库外键集合时发现 → 改成真检查并补 selfTest |
| 3 | `cart_product_exists` 的理由写成"SET NULL 外键"，生产库实际是 **NO ACTION** | 同上 |

第 2 条的代价比看起来大：它让第 9 轮的结论"**全库唯一没有外键保护的引用是
`after_sales.user_id`**"也一起错了 —— 实际是 **14 个**。

### 14-4 推翻前几轮结论：测试库与生产库的外键集合**不一致**

把生产库和测试库的外键逐条列出来对比：

| 列 | 测试库 | 生产库 |
|---|---|---|
| `carts.bundle_id → bundles` | **SET NULL** | **无外键** |
| `carts.product_id → products` | **SET NULL** | **NO ACTION** |
| `carts.user_id → users` | SET NULL | SET NULL ✅ |

原因：测试库是 `sequelize.sync()` 按**模型定义**建的，模型里有这些关联；
生产库是手工 DDL 建的，这些 FK 从来没补上。

影响：
- 体检项的**自证在两个库上跑的约束条件不同**（测试库插不进悬空行，生产库能）；
- 第 9 轮那份"外键覆盖"表**是照着模型定义写的，不是照着生产库查的** ——
  于是 4 个"防御项"的理由写错、1 个检查被误标成不可能发生。

**这一轮只做认知修正，没有动生产库的表结构**（加外键属于结构变更，
且存量数据要重新校验，风险不在"扒拉问题"该动的范围内）。

生产库实测：14 个无外键保护的 `*_id` 列，**当前悬空行数全部为 0**。

### 14-5 复核为误报（本轮查过但**不是** bug 的）

- **"删组合包会把客户整个结算卡死"** → 证伪：前端 `availableCartItems` 已过滤失效行。
- **"sharp 模块在生产上坏了"** → 旧日志（Node 18 vs sharp 0.35 的老账）；
  `package.json` 把 sharp **精确锁定 0.33.5**，生产实测加载正常。
- **"游客账号复用路径还能签发令牌"** → 已修：复用分支只回手机号 + `accountReused`，不发 token。

### 14-6 方法论：不变量的"保证方"不一定是数据状态

一开始想给"购物车组合包行必须指向存在的组合包"加一条数据体检，
结果发现要自证就得在测试库里插一条违反外键的行 ——
而测试库的 FK 比生产库全，插不进去（PG 里 `DROP CONSTRAINT` + 同事务 `INSERT`
还会挂起）。

**停下来重新想：这��不变量的正确保证方是应用行为（删组合包时清理购物车行），
不是数据状态。** 那就该用**黑盒行为测试**守（删组合包 → 购物车行消失），
而不是用数据体检（体检只能证明"数据当前没坏"，证明不了"以后不会坏"）。

> 数据体检适合守**"数据被外部写坏"**的类目（脚本、迁移、并发、人工改库）；
> 应用自己制造的数据，用**行为测试**守更直接、也更便宜。

### 15-1 金额守恒：把"不多收钱"升级成"不多不少"

用**组合矩阵**实测（不是单点）：无优惠 / 商品直降 / 满减 / 券 / 满减+券 /
组合包（权重除不尽）+券 / 买多赠一 / 组合包+满减+券 —— 8 种组合全部成立。

**新增**：

- `tests/api/moneyConservation.test.js`：9 条用例，含一条**积分兑换单不被误报**

## 第 16 轮：业务时区可配 + 已删商品不复活（两项业务决策落地）

第 15 轮结尾列了两个"需要产品/运维决策、不属于扒拉问题"的点，用户拍板：
**下架不复活已删商品**、**今天依赖时间可配**。这一轮把它们落成代码。

### 16-1 业务时区可配（`business_timezone`）

**原来的问题**：所有"今天"都跟着**服务器进程的本地时区**走 ——
`new Date().setHours(0,0,0,0)` 与 `AT TIME ZONE '<服务器偏移>'`。
服务器换个时区，"今日营收"就跟着变；有夏令时的时区上，
固定偏移的日分桶还会与日历日筛选**差一小时**。

**改造范围**（四个模块的"今天"口径，全部收口到一处）：

| 模块 | 原来 | 现在 |
|---|---|---|
| 统计日分桶 | `AT TIME ZONE '<服务器偏移>'` | `AT TIME ZONE '<配置时区>'`（IANA 名，PG 逐行求偏移，DST 也对） |
| 订单「今日营收」 | 服务器本地零点 | 业务时区零点 |
| 用户「今日新增/近7天/近30天」 | 服务器本地零点 | 业务时区零点 |
| 订单列表 / 导出 / 积分流水的日期筛选 | 服务器本地日历日 | 业务时区日历日 |

**关键实现细节**：
- 时区名会被拼进 SQL（`AT TIME ZONE '...'`）→ **只接受能通过 `Intl.DateTimeFormat`
  校验的真实 IANA 名**，非法值一律 400（顺带挡掉注入）；
- 日分桶用 **IANA 名而不是固定偏移** —— 固定偏移在 DST 时区上会逐行算错；
- **夏令时切换日本地日只有 23/25 小时**："本地日终点"必须按当地 23:59:59.999 单独换算，
  写成"起点 + 24h - 1ms"会漏掉/多算边界那一小时（这条是被 DST 测试当场抓出来的）；
- 统计缓存键**带上时区**，否则改完配置 15 秒内还会读到旧口径。

**默认值 `Asia/Shanghai`**：与生产服务器当前时区一致（实测 `Intl...resolvedOptions().timeZone = Asia/Shanghai`），
所以**升级后数字一个不变**；要按泰国时间运营，改配置成 `Asia/Bangkok` 即可。

**管理端**：系统配置页新增「业务时区」卡片（可搜索下拉 + 手动输入），三语文案齐全。

**测试**：
- `tests/api/businessTimezone.test.js`（7 条）：时区名校验（含 4 种注入尝试）、
  偏移（含美东冬夏令时）、日边界（含 23 小时的 DST 日）、日历日加减不溢出、
  7 天序列、SQL 表达式、配置读取与回退
- `tests/api/businessTimezoneWiring.test.js`（4 条）：**冻结时钟**后从 HTTP 入口证明
  「今日营收」与「日期筛选」真的跟着配置走、缓存不串味、配置接口拒绝非法时区名

### 16-2 已删商品不被上下架复活

业务约定：**上下架不复活已删商品，只有显式 `restore` 能让它回来。**

现状核查（三条路径）：
| 路径 | 行为 | 结论 |
|---|---|---|
| 批量上下架 | `Product.update` 默认带 `deleted_at IS NULL` → 已删行不参与 | ✅ 符合约定 |
| 改商品字段 | `findByPk(id, {paranoid:false})` → 能改到已删行，但 **deleted_at 不清** → 不会复活 | ✅ 符合约定 |
| `POST /:id/restore` | 显式 `paranoid:false` + 清 `deleted_at` | ✅ 唯一的复活路径 |

**风险在于"顺手"**：哪天有人为了"修批量上架不生效"加一句 `paranoid: false`，
删除这个动作就形同虚设（删了还能批量上架回来），而且当场没人会发现。

**已做**：
- 代码里把这条约定**写死成注释**（说明为什么这里故意不加 `paranoid: false`）
- 新增护栏 `tests/api/deletedProductNotRevived.test.js`（4 条）：
  批量上架不复活、批量下架不误伤、改字段不复活、只有 restore 能回来
- **反向验证**：故意加上 `paranoid: false` → 护栏立刻变红 ✅

### 18-5 功能优化盘点（基于生产库实测，不是凭感觉）

**实测前提**：生产数据量很小（9 单 / 18 商品 / 3 用户），所有热点查询都在 **0.1ms 内**，
当前的 seq scan 是小表的正确选择 —— **当下没有可测的性能问题**。
优化空间都在"数据长大后"，所以下面每条都有**证据**：

| # | 优化点 | 证据 | 做法 |
|---|---|---|---|
| O1 | `users.last_login_at` **无索引** | 生产库逐列核对：users 有 12 个索引，**没有 last_login_at** → 仪表盘"近 7 天活跃用户"每次**全表扫 users**（增长最快的表，且面板每 30 秒自动刷新） | 加迁移 `013_users_last_login_at_index`（CONCURRENTLY，不锁表） |
| O2 | 仪表盘**每个数字一条 count** | 实测发 **10 条查询**，orders 表**全表扫 5 遍** | 用 PG 的 `FILTER` 合并成 **6 条**，orders 只扫 3 遍；**口径一个数字都没变**（dashboard.actionable + revenueConsistency 用例逐项相等） |
| O3 | 超时清扫的 N+1 | 每单一个事务 + 行锁复查（2N 次查询） | **不改**：这是刻意的并发设计（与支付确认互斥），批量取明细会让"取到的明细已过期" → 重复回补库存。宁可慢，不可错 |
| O4 | 批量改状态的 N+1 | 每单 3 次查询（积分流水 / 余额 / 明细） | **已做**：整批流水与明细各一条查询拿完 + 余额行实例与积分服务共用。实测 10 单 **106 → 68 条**（见下） |

#### O4 的实现（以及一处被纠正的建议）

**做法**：
1. 整批订单的**购物积分流水**与**订单明细**各一条查询拿完
   （原来每单各查一次；earn 流水还被查了**两遍** —— 守卫一次、`restoreOrderResources` 内部又一次）；
2. 守卫查到的**余额行实例**传给积分服务复用 → 每单少查一次余额
   （行锁已经在手，实例里的 `balance` 会被服务就地更新 → 语义不变）。

**实测**：批量取消 10 单 **106 条 → 68 条**（-36%）。不可省的是每单的写操作
（库存 / 订单 / 流水 / 余额各一次 ≈ 5 条），省掉的是**读**：50 条读 → 16 条。

> ⚠️ **一处我原先的建议是错的，已纠正**：我最初说"按用户缓存余额行"——
> **不行**。前一张单回收积分后余额就变了，后一张单的守卫必须看到**最新**余额，
> 缓存会让守卫用旧值判断，可能放行本该拦的单。
> 正确做法是：**仍然每单读一次**，但把同一个**已加行锁的实例**同时交给守卫和积分服务。

**正确性护栏**（`tests/api/bulkCancelResources.test.js`，5 条）：
库存恰好回补 N 件 / 积分恰好收回 N 笔且余额 == 流水累计 / 券退回未使用 /
积分已被花掉的单被跳过而其余照常回补 / 查询条数 ≤ 80。

**反向验证**：撤掉优化 → BC-5 变红（106 > 80），而 BC-1~BC-4 仍绿
（它们守的是正确性，与性能无关 —— 这正是分开写的原因）。

**护栏**：新增 `dashboardQueryCount.test.js` —— 断言总览数据方法的查询条数 **≤ 8**
（当前 6）。守的是"形状"而不是"数字"：数字对不对有别的用例管，
这里管的是"又多写了一条 count"这种最容易犯的性能退化。
已反向验证：撤掉合并 → 10 条 → 护栏变红 ✅

## 第 19 轮：口径收口 + 安全边界复核 + 浏览器层核验

### 19-1 营收口径真正收口到**一份定义**

「营收 / 累计消费」出现在三个地方：面板的总营收/今日营收、订单列表的今日营收、
门户个人中心的累计消费。历史上它们**各写一遍口径** → "同一个指标在四个地方四个数"。

现在统一到 `constants/revenueStatus.js` 的两个函数：
`revenueWhere(Op, extra)`（Op 版）与 `revenueStatusSql(escape)`（SQL 片段版，给 PG 的 FILTER 用）。

**顺带补上一个口径缺口**：门户一直**显式**排除积分换购单，面板与订单列表没有 ——
口径靠"积分单金额恒为 0"这个隐含前提撑着。生产实测没有积分单，
但一旦出现历史遗留的积分单（金额非 0），同一个指标就会两个数。
现在三处一律排除 points。

> ⚠️ 踩了个坑：`sequelize.escape` 是**实例方法**（内部用 `this.dialect`），
> 当函数值传出去会丢 `this` → 面板 500。必须传 lambda。

**护栏**：`tests/api/revenueMetricConsistency.test.js`（3 条）——
三处数字相等 / pending+cancelled 不计 / 金额非 0 的积分单也不计。
反向验证：把面板的 points 排除去掉 → RM-3 变红（600 vs 100），RM-1/RM-2 仍绿。

### 19-2 SSRF 防护复核（结论：**无漏洞**）

用 24 种绕过手法逐一试：十进制/十六进制/八进制/短形式 IPv4、IPv6 各种映射写法、
`file://`、`gopher://`、带凭据的 URL、云元数据地址、CGNAT、基准测试段、广播地址 ——
**无一放行**。这块防护有 6 层（协议 → 解析后逐个 IP 检查 → 连解析出的 IP 防 DNS 重绑定 →
手动跟随重定向且每跳重查 → 超时与体积上限 → magic bytes 校验），很扎实。

但现有用例没覆盖"同一台机器的另一种写法"（将来有人把 `new URL()` 换成手写解析就会失守）
→ 补成 RI-11 / RI-12 两条护栏。

### 19-3 E2E 全套核验：56 条全过（2.5 分钟）

浏览器层的安全网一直不在部署门禁里（需要浏览器 + 起服务），但它是唯一能覆盖
"真实点击 + 真实渲染"的层。这一轮实测 **56 条全过** ✅。

### 19-4 一个"有依据的不做"

仪表盘的总营收是全表聚合 → 想过加**部分函数索引**
（`ON orders (COALESCE(total_amount_thb, total_amount)) WHERE status NOT IN (...)`）。
实测 20 万行：加索引前 **14ms**、加索引后 **14ms** —— PG 仍然选 Seq Scan
（聚合本身就是一次顺序扫描，索引扫描反而更慢）。

**没有证据支持它，只会给每次写订单加索引维护成本 → 不加。**

> 优化不是"能加就加"，是"**测过确实更快才加**"。测不出来收益的索引是纯负债。

## 第 21 轮：并发竞态（地址默认项）+ 确定性并发探针

### 21-1 真 bug：两个设备同时设默认 → 默认地址可能凭空消失

设默认是「先清理该用户**所有**地址为非默认，再把目标设为默认」**两步**，
而这两步之间**没有锁**。两个设备同时操作（双击 / 两台手机）会交错：

```
T1 清理全部 → T1 设 A → T2 清理全部（把 A 又清掉）→ T2 设 B
```

结果可能是**两个默认地址**，或**一个默认都没有**。
实测 60 轮并发里 **4 轮出现"没有默认地址"** —— 用户的默认地址凭空消失，
结算页的地址也跟着变空。

合作方地址那边一直锁着 Partner 行（`partnerPortalController`），用户这边漏了。

**修法**：四个会动默认项的地址写操作（新建 / 改 / 删 / 设默认）都先锁**用户行**
（`FOR UPDATE`），把同一用户的整段操作串行化。
锁用户行而不是地址行：地址行之间没有父子关系，锁地址行挡不住"清理全部"那一步。

### 21-2 更有价值的收获：**怎么写一个不会"假绿"的并发护栏**

第一版护栏是"跑 60 轮并发，看最终是不是恰好一个默认"。结果：

- 无修复时的**触发率只有 0.7%**（150 轮 3 并发才出现 1 次）→ 单次运行大概率抓不住
  → **靠概率的护栏就是"永远绿的测试"**（第 12 轮的主题又回来了）；
- 改成"另一个事务锁住用户行，看请求会不会阻塞" → **仍然假绿**，而且原因很隐蔽：
  `addresses.user_id → users.id` 是外键，PG 在 UPDATE 地址行时会顺带对 users 行加
  **KEY SHARE** 锁，而 KEY SHARE 与 **FOR UPDATE 冲突** → 即便接口没拿 FOR UPDATE 锁，
  请求照样阻塞 → 断言"它阻塞了"照样成立。

**最终手法（确定性，不靠概率）**：blocker 用 **FOR NO KEY UPDATE** ——
它与 FOR UPDATE 冲突、但**不与 KEY SHARE 冲突** → "阻塞"就只可能来自
接口自己拿的 FOR UPDATE 锁。另两个坑也堵了：连接池冷启动（先热身）、
窗口太短（1200ms + 断言窗口内确实没完成）。

**反向验证**：撤掉修复 → AD-1/AD-2 **确定性变红** ✅（不是概率性）。

### 21-3 同一批"静默错误结果"

这两轮抓到的问题有个共同点：**接口不报错，数字却悄悄不对** ——
最危险的一类（用户看到"我没有订单"，其实是自己传错了筛选）。

- 用户端订单列表 `?status=paid,completed` 静默返回 0 条（管理端却支持多状态）
- 地址并发设默认静默丢掉默认项

已分别用护栏钉死。

### 22-1 自检发现的漏改：前端兜底路径还在用本地时区

## 第 23 轮：留存清理归档积分流水的并发一致性

### 23-1 隐患：归档净额与实际删除的净额可能对不上

清理积分流水时必须把**被删流水的净额**记到余额行的 `archived_delta`，
否则「余额 = 剩余流水累计 + archived_delta」不成立 → **每日体检永久报红**
（用户看着"账不平"，其实是清理脚本的锅）。

原来是「先算净额 → 再记账 → 再删」三条**独立语句**（各自一个事务）。
READ COMMITTED 下每条语句取自己的快照：汇总之后、删除之前若有**并发写入积分**，
那条新流水会被删掉，但归档净额里没有它 → 恒等式被破坏。

**修法**：一批的「锁余额行 → 汇总 → 记账 → 删除」放进**同一个事务**，
且先锁住受影响用户的余额行（FOR UPDATE，与 pointsService 的 `lockOrCreateBalance`
同一把锁）→ 并发写积分排队等待 → 汇总看到的集合 = 实际删掉的集合。
锁顺序按 user_id 升序（全站约定）。

> ⚠️ **行锁必须与汇总在同一事务里才有意义** —— 各自独立语句时锁立即释放，等于没锁。

### 23-2 反复踩的坑：**"阻塞"不等于"在等锁"**

这轮为了给并发修复写一个**确定性**护栏（三轮下来第三次遇到），连续踩了三个坑：

| 坑 | 现象 | 解法 |
|---|---|---|
| 连接池冷启动 | 第一个请求要建连接，看起来像"被锁住" | **先热身**再计时 |
| 外键的 KEY SHARE 锁 | `addresses.user_id → users.id` 让 UPDATE 顺带拿 KEY SHARE，而它与 FOR UPDATE 冲突 → 即便接口没拿锁也会阻塞 | blocker 改用 **FOR NO KEY UPDATE**（与 FOR UPDATE 冲突、但不与 KEY SHARE 冲突） |
| 两种实现都阻塞 | 有锁/没锁都会卡住 → "它在阻塞"这个断言区分不开 | 看 `pg_stat_activity` 里**卡在哪一句**：修好后卡在 `SELECT ... FOR UPDATE`，没修则卡在 `UPDATE ...` |

护栏 `retentionArchiveConsistency.test.js`（4 条）：恒等式成立 / 归档净额精确 /
并发写入仍成立 / **清理在汇总之前就锁住余额行**（确定性判别）。
反向验证：撤掉修复 → RA-4 确定性失败 ✅

## 第 24 轮：通用 fuzz 探针（把"手挑接口"变成"全量扫"）

第 15 轮是**手挑**几个接口发现的"超长输入 → 500"。手挑的问题是：
将来新增接口时，谁知道它有没有同样的毛病？

于是写了个**通用**探针（`tests/api/writeEndpointFuzz.test.js`）：
用项目自己的 `collectRoutes(app)` 取出全部写路由，
每个接口都用 9 组恶意入参打一遍，断言两件事：

1. **不许返 5xx**（输入问题被当成服务端故障）
2. **响应里不许泄漏内部细节**（堆栈帧 / PG 错误文本 / SQL 片段）

它当场抓到第 15 轮那类问题的一个**漏网之鱼**：
`POST /api/system-config` 传超长值 → **500「设置配置失败」**（这接口没接错误翻译层）→ 已修为 400。

### 探针自己踩的两个坑（都写进注释了）

| 坑 | 现象 | 解法 |
|---|---|---|
| 恶意字符串太长 | 200KB × 30 字段 = 6MB → **被请求体上限（1MB）挡成 413**，请求根本没进控制器 → 探针形同虚设（第 15 轮那类 bug 反而测不到） | 改成 **300 字符**（刚越过字段上限、请求体仍在限额内） |
| 字段清单不全 | 清单里**没有 `username`/`login`** → 那正是第 15 轮出问题的字段 | 补全 30 个常见字段名 |

> 一个探针自己"看起来在测、其实测不到"，和第 21 轮的并发探针是同一类病：
> **断言成立的原因，必须确认是"被测的那个原因"。**

反向验证：把某接口的 catch 改成永远 500 → 探针当场抓到 ✅
（管理员接口抓不到，是因为第 13 轮的密码策略校验在模型校验之前就 400 了 —— 那是好事）

## 第 27 轮：两个遗留决策落地

### 27-1 业务时区默认值 → Asia/Bangkok

默认从 `Asia/Shanghai` 改为 **`Asia/Bangkok`**（泰国，UTC+7）：

- 店铺的**客户、计价货币（THB）、主要语言**都在泰国；
  泰国时间 23:30 的单属于**泰国的那一天** —— 按中国时区算会被推到下一天，
  与平台/物流的日结对不上。
- 关键：**它仍然只是一个默认值**，运营在管理端「系统配置 → 业务时区」随时可改
  （改的是配置项，不是代码）。生产库已**显式写入** `business_timezone=Asia/Bangkok`，
  这样它在管理端**看得见、也改得动**，不依赖代码默认值。

### 27-2 批量取消：先取性能数据，再决定动不动

| 批量 | 查询数 | 耗时 |
|---|---|---|
| 10 单 | 68 | 42ms |
| 50 单 | 308 | 87ms |
| 200 单 | 1208 | 213ms |

≈ **6 条/单**，拆开看：
- 5 条是**必须的写**（订单更新、库存回补、积分流水、余额更新）
- 1 条是**必须的余额读** —— 余额随每单回收而变，**不能跨单缓存**（第 21 轮已确认）

→ **不可压缩**，且 200 单不到 0.25 秒 → **数据表明：不需要再优化，保持现状**。

> 这一轮的结论是"**不动**"—— 但它是**有数据支撑的"不动"**，
> 而不是"没查就不动"。

### 28.4 真缺陷（7 个，全部已修）

| # | 缺陷 | 影响 | 修法 |
|---|---|---|---|
| 1 | `pg_scalar` 继承调用方 stdin | 循环里逐条查表时 psql 把循环输入读走 → **静默只比对第一张表**，后面全跳过且不报错 | `< /dev/null` 掐断 stdin |

### 28.6 两条"形同虚设"的护栏（这一轮最有价值的发现）

这两条不是新功能缺失，而是**已存在的护栏其实从没执行过** —— 比没有护栏更危险。

**① Redis 契约 4 条用例在常规回归里从未执行**

判定是 `const hasRedis = Boolean(process.env.REDIS_URL)` —— 只看**环境变量在不在**，
不看 Redis **在不在**。CI/本地通常不设 `REDIS_URL` → 这 4 条永远 skip。
而它们守的正是"Redis 版与内存版类型契约不一致 → 生产 500"这个**已经发生过的真实缺陷**。

修：改成**探测可达性**（`net.connect` 探 host:port，500ms 超时）。
本机 Redis 本来就在跑 → 护栏从"永远跳过"变成"每次都跑"。

**② 契约用例跟着 `createSharedStore` 切后端 → 永远只有一个后端被测**

`createSharedStore` 随 `REDIS_URL` 的有无返回 MemoryStore 或 RedisStore。
契约用例调用它，于是：设了 `REDIS_URL` 就只测 Redis、不设就只测内存，
而且**用例名还写着"内存后端"，实际测的是 Redis** —— 静默的语义漂移。

修：新增 `createMemoryStore()` / `createRedisStore()` 显式点名后端，
契约用例对两个后端**各跑一遍**（8 条 → 16 条）。

**验证可证伪**：把 Lua 改回带引号的写法（复现第 7 条那个 bug），
测试如期变红，且**只红 Redis 后端的 SS-5**，内存后端仍绿 —— 说明两个后端确实被分别覆盖。

### 28.7 生产侧两条差点误判的发现

**① error.log 里那条 sharp 报错是历史遗留，不是"生产图片压缩全挂"**

堆栈写着 `Could not load the "sharp" module ... Requires >=20.9.0`，
生产是 Node 18.20.8 → 一眼看去像"sharp 在生产完全不可用，图片处理全挂"。
但实测：

- `node_modules/sharp/package.json` 是 0.33.5，engines `^18.17.0 || ^20.3.0 || >=21.0.0` → **满足**
- `node_modules/@img/sharp-linux-x64` 是 0.33.5 → 满足
- 堆栈指向的 `node_modules/sharp/dist/sharp.mjs` **根本不存在**（0.33.x 是 `lib/` 结构，
  `dist/sharp.mjs` 是 0.35 才有的）→ 这条堆栈来自**旧版 sharp 时代**
- 在生产直接跑 `processImageFile()`：507ms 正常产出 main/thumb/mid ✓

也就是说：**报错是旧版本留下的历史日志，当前生产 sharp 是好的**。
如果只看堆栈就下结论，会误报一个"生产功能全挂"的大问题。

（代码里本来就做了降级：sharp 懒加载，失败只 warn 不致命，
文件头注释也写着"sharp 0.35 要求 Node ≥20.9，而生产机是 Node 18"。）

**② 全量核对图片引用时，抓到 1 个真实的 404**

核对 19 个指向 `/uploads` 的引用（18 商品 + 1 头像）时，发现 id=1 的商品主图
`product_1758200061313-648966103.webp` **在磁盘上不存在** ——
库里存的是 .webp，磁盘只有原图 .jpg（Nov 6 09:32 的时间戳 = 迁移当天）。

成因：Nov 6 那次迁移把 uploads 的**原图**搬过来了，但派生的 `.webp` 没搬，
而库里记的是 `.webp` → 该商品图片一直是 404。

修：实测 sharp 时顺带把它生成了（文件名规则与库中引用完全一致），
HTTP 抽查 `/uploads/products/product_1758200061313-648966103.webp` → **200**。
现在 19/19 图片引用全部存在。

顺带查实：部署脚本 `rsync -a --delete --exclude 'public/uploads/'` —— **不会**删生产图片 ✓
（我一度怀疑是部署删的，读了脚本才排除）。

## 第 30 轮：分页一致性与跨库结构漂移

这轮的角度：**同一件事在不同地方做成了两样**。前几轮修的是"某个接口算错了"，
这轮找的是"同一个约定只在一半地方落实了"。

### 30.1 深翻页：统一工具写好了，却只用在了一半地方

项目里有统一分页工具 `src/server/utils/pagination.js`，它**明确处理了深翻页**：

```js
if (page > maxPage) page = maxPage          // maxPage = 10000
if (offset > maxOffset) { offset = maxOffset ... }   // maxOffset = 100000
```

工具的注释把风险讲得很清楚：

> page 也必须有上限：limit 有上限但 page 没有时，`page=999999999` 会产生近亿 OFFSET
> —— PG 必须顺序扫过整表再丢弃，叠加 findAndCountAll 的 COUNT(*) 就是两次全表扫描。

但扫遍所有控制器后发现：**26 个控制器里只有 7 个用了这个工具**，
另外 **6 处是各自手写的**，而且手写的版本**只有下限、没有上限**：

| 位置 | 手写解析 |
|---|---|
| `orderController.getMyOrders`（用户端我的订单） | `Math.max(1, parseInt(req.query.page, 10) \|\| 1)` |
| `pointsController.listTransactions`（积分流水） | 同上 |
| `productCategoryController.listAdmin`（后台类别） | 同上 |
| `partnerAdminController.listPartnerOrders`（后台合作方订单） | 同上 |
| `partnerPortalController`（商品列表 / 订单列表） | 同上 ×2 |

`?page=999999999&pageSize=100` → offset ≈ 1e11 → **PG 顺序扫全表两次**。

修法：6 处全部改走 `resolvePagination`，保留各自原有的默认值与上限语义
（`limit` vs `pageSize` 参数名、默认 10/20/5、上限 100/50 都没变）。

### 30.2 跨库结构漂移：生产与测试**只有一处**不一致

第 14 轮吃过一次亏："测试库和生产库不一样"。这次把它做成**可复现的检查**：

```bash
# 两个库各导一份 (表.列 :: 类型) 再 diff
psql -d shop_dev  -Atc "SELECT table_name||'.'||column_name||' :: '||data_type
                      FROM information_schema.columns WHERE table_schema='public' ORDER BY 1"
psql -d shop_test -Atc "同上"
```

生产 311 列 vs 测试库 310 列，差异**只有 3 处**：
- `orders.shipped_at`：生产 `timestamp without time zone` / 测试 `timestamp with time zone` ← **真漂移**
- `schema_migrations.*`：生产有迁移表，测试基建不建 → 正常
- `HookProbes.*`：测试基建的探针表 → 正常

根因：迁移 003 用手工 DDL 加的列是 `TIMESTAMP`（无时区），
而模型里 `shipped_at: DataTypes.DATE` 在 PG 里映射成 `timestamptz`。
**测试基建用 `sequelize.sync()` 按模型建表 → 测试库是对的、生产是错的** → 测试永远测不出生产的问题。

### 30.3 naive 列的写入语义（实测，不是推断）

同一个 naive 列，两种写入方式存的东西不一样：

| 写入方式 | 写入 `2026-11-18T15:43:25Z` → 库里存 |
|---|---|
| Node 写（模型 `new Date()` → node-postgres 序列化成带时区 ISO，PG 插 naive 列时丢掉时区标记） | **2026-11-18 23:43:25**（本地墙上时间，本机 +08） |
| PG 侧 `now()`（会话时区 +00） | **2026-11-18 15:43:50**（UTC） |

同表两种时间来源**差 8 小时**。

后果（泰国站点，浏览器在 UTC+7）：后台"发货时间"会比真实时间**晚 8 小时**。

### 30.4 修复

- 迁移 `014_orders_shipped_at_timestamptz`：naive → timestamptz，
  历史值按 **Node 进程本地时区**解释（`AT TIME ZONE 'Asia/Shanghai'`）。
  ⚠️ 用错基准会再偏 8 小时：**不是** PG 会话时区（生产是 UTC），
  因为写入时存的是"本地墙上时间"。
  幂等：已是 timestamptz 直接跳过（重复转换会把值平移一个偏移）。
  生产该列 9 个订单**全为 NULL** → 转换零数据风险。
- 6 处分页统一走 `resolvePagination`。

### 30.5 查实"没问题"的（避免虚报）

| 项 | 手段 | 结论 |
|---|---|---|
| 前端 XSS 落点 | 全量扫 `v-html` / `innerHTML` / `new Function` / `eval` | **零命中**（三个前端都没有） |
| 路径遍历 | 扫 `path.join(req.*)` / `res.sendFile` | 只有三处固定文件名，安全 |
| 原始 SQL 拼接 | 扫 `sequelize.query` + 模板串 | 只在 migrations 里（内部常量，无用户输入） |
| 错误信息泄露 | 扫 `message: e.message` / `stack` | 全部是**带 status 的业务异常**才回显；无 stack 外泄 |
| 其余分页点 | 逐个查 limit/pageSize 来源 | 全都有 `Math.min(上限, …)` |

### 30.6 生产实测（部署后）

- 迁移 014 在生产启动时自动执行：`✅ 已执行迁移: 014_orders_shipped_at_timestamptz`
- `orders.shipped_at` → `timestamp with time zone` ✓
- 全库 naive 业务列只剩 `schema_migrations.applied_at`（迁移表自身，无业务含义）✓
- **写入语义实测**（事务内验证并回滚，无残留）：
  写 `2026-01-02T03:04:05.000Z` → 库里存 `2026-01-02 03:04:05+00`，
  `shipped_at = '2026-01-02T03:04:05+00'` 为 **t**（瞬间正确，不再是本地墙上时间）
- 深翻页钳制实测：`page=999999999&pageSize=100` → `page=1001, offset=100000` ✅
- 24 项数据不变量全过；恢复演练 27 表一致；生产数据未变
  （3 用户 / 9 订单 / 9 明细 / 18 商品 / 2 合作方 / 1 管理员）；error.log 无新增

### 30.6 护栏（都做过反向验证）

- `tests/api/deepPaginationGuard.test.js`（8 条）
  - 断言**实际下发的 SQL** 里的 OFFSET 数值上限（不是"接口返回 200" —— 那是假绿）
  - 一条**防退化扫描**：控制器里不允许再出现手写的分页解析
  - 反向验证：去掉工具的钳制 → 接口层捕获到真实 OFFSET `99999999800` → 红；
    故意写一处手写分页 → 扫描护栏红
- `tests/api/shippedAtTimezoneGuard.test.js`（5 条）
  - SA-3 先把测试库的列**改回 naive** 再跑迁移 —— 否则只会走到"已转换"的跳过分支，
    那种永远绿的护栏最危险
  - 断言历史值按本地时区解释、重复执行不漂移
  - 反向验证：把 `AT TIME ZONE` 去掉 → 差值正好 `28800000` ms（8 小时）→ 红

## 第 31 轮：移动端布局实测（这次用真浏览器量，不靠想象）

前面几轮的前端工作多是**静态扫描**（找硬编码、找缺 aria-label）。
这轮换了手段：**开真浏览器、钉死移动视口、把布局量成数字**。

工具：内置浏览器（生产站点 + 本地构建产物），视口 390×844（iPhone 14）。

### 31.1 实测发现的三个真问题

**① 商品卡底部按钮被压成 3 行竖排（最严重）**

390px 下卡片宽约 170px，两个按钮并排后每个只剩 **65px 内容宽**
（`flex-1` + `px-3` 左右各 12px padding），
"Add to Cart" 换行成 **3 行**，"Buy Now" 2 行 —— 按钮区被撑到 **82px**（本该 44px），
卡片底部白白多出 38px，竖排文字更是没法看。

修：移动端**纵向堆叠**（`flex-col sm:flex-row`），sm+ 才并排；
两个按钮都加 `whitespace-nowrap`（任何语言下都不再折行）。

**② 标题/描述的固定占位高度留下空洞**

标题 `min-h-[3rem]`、描述 `min-h-[2.5rem]` 是为了卡片等高，
但卡片等高其实由 grid 的 `items-stretch` + 价格区的 `mt-auto` 保证，
占位只会让**短标题**的卡片下方空出一块（生产商品描述基本为空 → 每张卡白占一行）。

修：去掉两处 `min-h`，描述为空时整个 `<p>` 不渲染。

**③ 触控热区不足，且注释与实现对不上**

### 31.5 附带发现：一个**只在特定时刻**失败的测试（业务没错，测试错了）

跑全量回归时 DA-2/DA-3 红了：

```
AssertionError: expected 2 to be 1   （今日订单数）
AssertionError: expected 550 to be 50 （今日营收）
```

看起来像"今日口径"算错了。**其实业务代码是对的，测试把自己的假设写死在了本地时区上**：

- 测试用 `const yesterday = new Date(); yesterday.setDate(getDate()-1); yesterday.setHours(10,0,0,0)`
  → 这是**本地时区**（服务器 Asia/Shanghai = UTC+8）的昨天 10:00
- 业务口径是**业务时区**（Asia/Bangkok = UTC+7）的"今天"
- 于是在**本地 00:00–07:00** 这个窗口里，"本地昨天 10:00"正好落在**曼谷的今天**
  → 昨天那单被算进今天 → 用例必挂

也就是说：这个用例**每天有 7 小时是红的**，其余时间绿的 —— 典型的"随机失败"来源。

修：用业务时区工具直接算日历日

```js
const tz = await getBusinessTimezone()
const { y, m, d } = localCalendarDate(tz)
const prev = addDaysToCalendarDate(y, m, d, -1)
const at = (yy, mm, dd, hour) => new Date(localDayStartUtc(tz, yy, mm, dd) + hour * 3600 * 1000)
```

**验证**：换机器时区各跑一遍 —— `TZ=America/New_York`（UTC-5）、`TZ=Asia/Bangkok`（UTC+7）、
`TZ=Pacific/Kiritimati`（UTC+14）→ 9 条全过 ✓ 与执行时刻和机器时区都无关。

全库扫了一遍同类写法（`setDate(getDate()-1)` / `setHours(10`）：**只有这一处**，已清零。

### 这轮的方法论收获

1. **生产库实测比读代码硬**：外键覆盖、SET NULL 的合法状态、5 条软删商品的历史订单 —— 都是读代码看不出来的
2. **护栏测试的"永远绿"陷阱**：我加的第一版孤儿检查因为外键保护**根本不可能触发**，
   等于假检查 → 改成用唯一无外键的 `after_sales.user_id` 来证明它真能报
3. **扫描脚本本身会误报**：文本插值、slot 包装组件都要排除，否则噪声淹没真问题
4. **"检查全绿"本身需要被检查**：检查项要能自证会响（`selfTest`），
   或者说清"由什么约束保证"（`defensive`）—— 否则体检报告只是心理安慰

5. **"测了但没跑"和"没测"一样危险**：组合包数量回读的 bug 用例一直存在，
   只是回归漏了 `tests/integration` —— 少跑一套测试 = 把那一套里的真 bug 放行到生产。
   现在部署脚本带**回归门禁**（默认开启）。

6. **"测试库和生产库不一样"**：测试库是 `sequelize.sync()` 建的（按模型定义），
   生产库是手工 DDL 建的 —— 外键集合并不一致。照着模型定义写"外键覆盖"结论，
   等于照着错误的地图数路。**要查就查真正在跑的那个库。**

7. **"有备份文件"和"备份能恢复"是两件事** —— 只有真恢复一次（到临时库）才算数。
   判定基准还要选对：拿"恢复库 vs 生产库"比会永远误报（备份是时间点快照，生产一直在写），
   正确的基准是"备份快照 vs 恢复库"。

8. **观察方式本身会造假** —— 这轮两条"重大发现"其实都是我的观察错误：
   `ls | head` 截断了输出、把"宿主机没装 pg_dump"当成了"没法 pg_dump"。
   下结论前先确认**看到的是全部**；环境探查要问到能用的那层（容器里可能就有）。

9. **统一工具只落实了一半，比没有工具更危险** —— 分页工具有防深翻页的逻辑，
   但只有 7/26 的控制器在用；剩下 6 处手写的只有下限没有上限。
   下次做"统一"时，要**统计覆盖率**而不是"确认工具存在"。

10. **结构漂移要靠 diff 两个库，不靠读模型定义** —— 生产与测试的列类型全量 diff，
    311 列只差一处。那一处靠读代码根本看不出来（迁移 003 的手工 DDL vs 模型的 DATE）。
    同理，naive 列的写入语义必须**实测**（Node 存本地墙上时间 vs PG 侧 now() 存 UTC），
    我第一次的推断就是错的。

11. **布局问题必须量，不能看** —— 静态扫描 CSS 只能发现"写了什么"，
    发现不了"渲染成什么样"。开真浏览器、钉死视口、把尺寸量成数字，
    才知道按钮被压成 3 行、按钮区 82px、热区 36px。
    而且**同一轮的三个初判都被实测推翻了**（图片没填满、按钮没对齐、Tab 被裁切）
    —— 凭想象报"修好了"比不报更糟。

12. **注释也是契约** —— 顶栏 select 的注释写着「iOS 建议 44px」，
    实现是 36px。注释里的数字如果和代码不一致，后来的人会以为已经满足。
    写注释时要么让代码跟上，要么别写具体数字。

数据不变量（23 项：15 自证 + 8 防御）每次全过。
